# Итоговый отчёт: аудит безопасности StarRocks 4.1.7 на соответствие стандарту `db_dec.docx`

## 1. Executive Summary

StarRocks 4.1.7 (`b81ff9cc`) в конфигурации по умолчанию **не соответствует** стандарту. После рекомендованной
настройки (§11.2) часть нарушений устраняется. Остаются три класса ограничений, которые нельзя устранить
конфигурацией продукта:

1. **Защиту прикладных данных от администраторов СУБД (4.5) технически обеспечить нельзя.** Встроенная `db_admin`
   читает все данные, и роль неизменяема (F-01). `user_admin` выдаёт себе любые права и действует от имени любого
   пользователя (F-02). Обладатель `OPERATE` (по умолчанию и `security_admin`) может исполнять код в процессе FE
   (F-03). Привилегия `SECURITY` управляет источником идентичности (F-11). `root` неудаляем и обходит Ranger (F-04).
   Можно снизить, но не исключить: собственные роли, отключение Groovy, PAM, принцип двух лиц, мониторинг.
2. **Нет парольной политики и блокировки учётных записей** (4.8, 4.2, 5.1 — блокировка/разблокировка) (F-05).
   Компенсация — только внешняя аутентификация (LDAP/СУДИР) и PAM.
3. **Межузловые каналы (Thrift, BDB JE) не поддерживают TLS, узлы не аутентифицируют друг друга** (2.4) (F-09).
   Компенсация — сегментация и шифрование на уровне инфраструктуры.

Аудит (5.1/5.2) неполон: по умолчанию не пишутся входы и неуспешные попытки. Выход не пишется никогда, поля
«приложение» нет. Изменения конфигурации через HTTP не аудируются (F-06, F-07). DDL, DCL, создание/удаление
УЗ, `ADMIN SET CONFIG` и доступ к объектам регистрируются корректно, с маскированием паролей.

Найдено **14 нарушений/рисков** (F-01…F-14): 2 критических, 7 высоких, 4 средних, 1 группа гипотез.
12 подтверждены доказательно (10 из них — с динамическим подтверждением на стенде), 1 — вероятное (F-11).

Отдельно проверены **меры защиты из §11.2** (hardened-профиль с перезапуском FE/BE, `evidence/t_hardened.out`):
обязательный TLS блокирует незашифрованные внешние подключения (localhost остаётся исключением), `enable_http_auth`
закрывает анонимные HTTP-эндпоинты FE и BE и анонимное изменение конфигурации BE, отключение Groovy делает
`ADMIN EXECUTE ON FRONTEND` недоступным, модуль `connection` включает аудит входов и неуспешных попыток (выход
по-прежнему не регистрируется). Собственная роль «DBA без данных» (F-14) закрывает чтение данных по всем 12
проверенным путям.

## 6. Вывод по защите данных от администраторов (приоритет 1)

Инвариант: «администратор выполняет операции администрирования, но не получает содержимое данных».

| Модель | Исходные права | Получение данных | Механизм | Доказательство |
|---|---|---|---|---|
| A. db_admin | встроенная роль | **да, напрямую** | SELECT/EXPORT ON ALL TABLES | T-ADM-01 |
| B. root | встроенный | **да** | ALL; обход Ranger; неудаляем | T-AUTH-01, код |
| C. user_admin | GRANT, IMPERSONATE | **да, косвенно** | самовыдача, EXECUTE AS | T-ADM-03/04 |
| D. cluster_admin | NODE | не подтверждено | H-11 (изменение состава кластера) | T-ADM-08 |
| E. security_admin | SECURITY, OPERATE | **да, косвенно (стат.)** | Groovy в FE (F-03); IdP (F-11) | T-ADM-05/06 |
| F. внутренние сервисы | сеть кластера | **да (архитектурно)** | BE исполняет фрагменты без проверки пользователя | F-09 |
| G. пользователь с ошибкой авторизации | — | не обнаружено | PUBLIC и information_schema корректно фильтруются | T-PUB-01 |
| H. администратор ОС/хранилища | root ОС | **да** | файлы сегментов/BDB JE; шифрования at rest не найдено | архитектура |
| I. сговор | C+E | да | F-02 + F-11 | — |

**Заключение по 4.5:** при текущей архитектуре 4.1.7 инвариант не обеспечивается для встроенных ролей `root`,
`db_admin`, `user_admin`. Для `security_admin` он не обеспечивается до отключения Groovy. Собственная роль
«DBA без данных» (F-14, тест T-ADM-09 выполнен) по конфиденциальности работает: ни один из 12 путей чтения не дал
значений данных при условии отсутствия SELECT/INSERT/EXPORT и SYSTEM-привилегий и отключённого Groovy. Остаются
утечки метаданных (имена секций при автосекционировании, статистика), контроль целостности через ALTER и
непроверенные коннекторы внешних каталогов (H-10c).
Требование 4.5 следует оформить как риск КБ по п. 2.1 (типовой риск «доступ с повышенными привилегиями»).
Минимизация: PAM, запись сессий, DAM, принцип двух лиц для GRANT/SECURITY/OPERATE и корреляция событий в ПКБ.

## 7. Аутентификация и авторизация

* SQL-аутентификация обязательна, но пустые пароли допустимы, включая `root` по умолчанию (F-04, F-05).
* Native-пароли — MySQL `mysql_native_password` (SHA-1 без соли). Политики длины, срока и блокировки нет (F-05).
* Внешняя аутентификация (LDAP/JWT/OAuth2) — через `SECURITY INTEGRATION` и `authentication_chain`. Ошибки IdP
  не приводят к fail-open (H-22). Конфигурацией IdP управляют `db_admin` и `security_admin` (F-11).
* HTTP: при `enable_http_auth=false` (по умолчанию) часть FE-эндпоинтов и административные BE-эндпоинты
  анонимны (F-06, F-08). При `true` BE делегирует проверку FE (`checkAuth`) с привилегией OPERATE/NODE.
* Внутренние RPC (Thrift, BRPC) не аутентифицируются (F-09).
* RBAC: роли с наследованием; роль PUBLIC по умолчанию минимальна (4.12 — С). Встроенные роли совмещают
  обязанности (F-01, F-02).

## 9. Аудит

Регистрируется (С): создание/удаление УЗ, GRANT/REVOKE, ALTER USER, DDL, `ADMIN SET CONFIG`, SELECT/DML.
Поля: `Timestamp`, `User`, `AuthorizedUser`, `Client`, `feIp`, `Stmt`, `State`, `ErrorCode`. Пароли
маскируются. Атрибуция после `EXECUTE AS` сохраняется.

Не регистрируется: вход и неуспешный вход (по умолчанию; включается модулем `connection`), выход (никогда),
блокировка/разблокировка (механизма нет), HTTP-изменения конфигурации FE/BE, все действия на уровне BE.
Поля «приложение» нет.

Хранение: файл `fe.audit.log`, 30 дней (`audit_log_delete_age`), без встроенной отправки в ПКБ. Защита —
правами ОС. Администратор с OPERATE (F-03) потенциально может влиять на журналы FE.

## 10. Непроверенные направления и ограничения

См. `coverage.md` §1, §4. Главное: плагины, UDF runtime, BACKUP/EXPORT, внешние каталоги, контекст VIEW/MV,
по-методный разбор `FrontendServiceImpl` и `PInternalService`, JWT/OAuth2, shared-data, шифрование at rest, SCA.
Покрытие атомарных критериев: 71 % с доказательным статусом, 8 % не подтверждено, 21 % — эксплуатационная
проверка. Эксплуатация уязвимостей не выполнялась (audit_scope.md §4).

## 11. Рекомендуемые изменения

### 11.1. Исправления кода (запросы вендору)
1. Встроенная роль администрирования без DQL/DML/EXPORT; изменяемые встроенные роли (F-01).
2. Запрет самовыдачи GRANT; IMPERSONATE вне `user_admin`; принцип двух лиц для GRANT/SECURITY (F-02, F-11).
3. `enable_execute_script_on_frontend=false` по умолчанию; отдельная привилегия (F-03).
4. Парольная политика (длина, сложность, срок, история), `ACCOUNT LOCK/UNLOCK`, блокировка по неуспешным
   попыткам, `caching_sha2_password` (F-05).
5. События DISCONNECTION, поле «приложение» (`program_name`), аудит HTTP-конфигурации и BE-операций,
   syslog/CEF-выход (F-07).
6. TLS и взаимная аутентификация для Thrift, BDB JE, BRPC; минимальная версия TLS задаётся в коде (F-09, F-10).

### 11.2. Необходимая конфигурация (эталонный профиль)

`fe.conf`:
```
enable_execute_script_on_frontend = false
enable_http_auth = true
enable_https = true
ssl_keystore_location = <path>.jks
ssl_keystore_password = <secret>
ssl_key_password = <secret>
ssl_force_secure_transport = true
ssl_cipher_whitelist = <AEAD-наборы по /6/>
audit_log_modules = slow_query, query, connection
audit_log_delete_age = 35d
authentication_ldap_simple_ssl_conn_allow_insecure = false
authentication_ldap_simple_ssl_conn_trust_store_path = <truststore>
enable_udf = false
```
(в образе `allin1` по умолчанию `enable_udf = true` — исправить, см. F-14)

`be.conf`:
```
enable_http_auth = true
enable_https = true
ssl_certificate_path = <cert>
ssl_private_key_path = <key>
enable_token_check = true
```
SQL после установки: смена пароля `root` и хранение в PAM; не выдавать `db_admin`, `user_admin`, `security_admin`
людям; собственная роль «DBA без данных» вместо `db_admin` (F-14); периодическая проверка `SHOW GRANTS FOR ROLE public`.

Все перечисленные меры проверены на стенде (`evidence/t_hardened.out`, `t_aud04.out`): T-TLS-04, T-HTTP-04,
T-AUD-04, T-ADM-05 — работают. Непроверенное на целевой конфигурации: T-TLS-05 (трафик межузловых каналов),
T-AUTHZ-02 (устаревание прав в открытой сессии).

### 11.3. Внешние компенсирующие контроли
* PAM для всех ПУЗ (включая root) с записью сессий; доступ 3-й линии — только через PAM (4.13–4.15).
* DAM-агент (5.6), закрывающий выход из сессии, имя приложения и прямой доступ.
* Агент доставки `fe.audit.log` в ПКБ в реальном времени. Корреляционные правила: GRANT самому себе,
  `EXECUTE AS`, `ADMIN EXECUTE`, `CREATE/ALTER SECURITY INTEGRATION`, `ADMIN SET ... authentication_chain`,
  `INSTALL/UNINSTALL PLUGIN`, `BACKUP`/`EXPORT`.
* Сетевой ACL: 9030/8443 — для клиентов и PAM; 8030/8040/8060/9010/9020/9060/9050 — только между узлами
  кластера; шифрование межузлового трафика средствами инфраструктуры.
* Права ОС: отдельный непривилегированный пользователь FE/BE, `0600` на журналы и `meta`, FIM на `*.conf`.
* Шифрование данных at rest (LUKS / SSE-KMS) против модели H.

### 11.4. Архитектурные изменения
* Отдельный кластер на АС/категорию данных (2.3).
* Внешняя аутентификация (СУДИР/LDAP по ldaps) для всех пользователей, native — только break-glass root (4.8).
* Изолированный сетевой сегмент кластера (TB1) как обязательное условие эксплуатации (F-09).

### 11.5. Принципиально неустранимые ограничения текущей архитектуры
* `root` с полными правами, неудаляемый и необходимый для выдачи `root`/`cluster_admin` (4.5).
* Неизменяемые встроенные роли с доступом к данным (4.5).
* Отсутствие блокировки и парольной политики native-УЗ (4.8, 5.1).
* Отсутствие TLS и аутентификации на Thrift/BDB JE и аутентификации на BRPC (2.4, 4.3).
* Авторизация только на FE: BE/CN не проверяют права пользователя.
* Отсутствие события выхода и поля «приложение» в штатном аудите (5.1, 5.2).

## 13. Заключение о применимости

Использовать StarRocks 4.1.7 в корпоративной среде при модели угроз, где администратор СУБД не должен
получать прикладные данные, **можно только как принятый риск КБ** (п. 2.1) и только при выполнении всех условий:
1. профиль конфигурации §11.2 применён и проверен тестами test_plan.md;
2. встроенные административные роли не выданы людям; `root` — только break-glass через PAM;
3. кластер изолирован сетевым сегментом с шифрованием межузлового трафика;
4. все ПУЗ работают через PAM; установлен DAM; аудит в реальном времени доставляется в ПКБ с правилами §11.3;
5. пользователи аутентифицируются через СУДИР/LDAP (ldaps), а не native-паролями.

Для зон PCI DSS и АС финансовых услуг (4.8, 5.6) без исправлений вендора по F-01, F-05, F-07 и F-09
соответствие требованиям **не достигается**. Рекомендуется не размещать такие данные без отдельного решения
владельца риска.
